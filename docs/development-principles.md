# 制作の前提概念：非エンジニアのAI個人開発の実践手順

VINYL ARCHIVE をブラッシュアップしてローンチするまでの、制作上の前提となる考え方。
AIエージェント（Claude Code / Codex）に作業を依頼するときも、この方針を土台にする。

出典: [非エンジニア経営者のための「実践AI開発術」：完成までの11ステップ（PIVOT TALK TECH／梶谷健人氏）](https://pivotmedia.co.jp/movie/15167)
※出典の内容を要約・再構成したもの。引用ではなく、このプロダクト向けに言い換えている。

---

## 1. 根底にある考え方

- **コードを書く力より「課題の解像度・企画力・デザインの意匠」が勝負を分ける。** 実装はAIが代行できる。人間は「何を創るか」「妥協しない価値は何か」の意思決定に集中する。
- **個人開発の強みは試行回数とスピード。** 説明コストがなく、作って、市場の反応を見て、直す、を高速に回せる。
- **作るハードルが下がった後は「届ける力」が重要になる。** 制作過程の発信やファンづくりなど、アテンションを事業に変える視点を持つ。
- **経営者（作り手）自身がAIに直接指示する。** 伝言による妥協や認識のズレを避け、理想をそのまま形にする。

## 2. 事業・企画の方針

- AIが裏側で動くサービスにはAPI利用料などの原価がかかる。**完全無料のモデルは成立しない**前提で設計する。
- 狙う領域は次の両方を満たすところ。
  - 既存のAI単体だと「絶妙に不便」
  - ユーザーがすでに、時間や外注費のためにお金を払っている
- 大企業に模倣されないよう、参入障壁ができるまでは**あえて目立たず育てる**戦略も選択肢。

## 3. 動画の手順（詳細）

注記: 動画タイトルは「11ステップ」だが、公開ページの本文には番号付きの11項目は載っていない。番号が付いているのは初期セットアップの3手順だけ。以下は、本文にある6つの話題の順に、手順・判断基準・指示の出し方を整理したもの。動画本編でしか語られていない内容は含まれていない可能性がある。

### 3-1. 背景：なぜ今ひとりで作れるのか

- **ソロプレナー**とは、AIツールを組織の手足として使い、単独または極少人数でスタートアップ並みの収益を出す事業主のこと。
- 海外の事例として、カロリー計算アプリ「Cal AI」を立ち上げた若手起業家が、年間売上見込み約75億円を記録し、大手企業へ事業を売却した。
- 急成長しているソロプレナーの**約半数は非エンジニア出身**。コーディングはAIが代行するため、ユーザーのペインを突く企画力とUIの意匠に強い人が有利になる。
- 個人開発の強みは、投資家やチームへの説明コストがないことと、**月1本以上のペースで試行回数を稼げる**こと。市場の反応を見て直す速度が、大資本に対する防壁になる。
- 参入障壁ができるまで目立たず伸ばし、大企業の安易な模倣を避ける戦略もある。
- **YouTuberの台頭と同じ構造**。撮影・編集のハードルが下がったのと同様に、開発のハードルが崩れた。作るのが簡単になると、勝敗は「届ける力」（アテンションのマネタイズ）に移る。SNSで制作過程を公開し、ファンを巻き込める人が有利。
- 課題への解像度と熱量が最も高い経営者本人がAIに直接指示すれば、伝言による妥協や認識のズレがなくなる。

### 3-2. 初期セットアップ（原文で番号付きの3手順）

1. デファクトスタンダードの Claude Code または Codex をPCにインストールする。
2. AIの作業場となる空のフォルダをPC上に1つ作り、そのツールで開く。
3. 解決したい課題やこだわりを、音声入力など自然な日本語でAIに直接伝える。

考え方: AIにとってフォルダは自分の執務室。部下に話しかけるように要件を伝えれば、最初の土台ができる。最初は、日頃の小さな不便を解消するツールを1本作ってみて、開発の確信を得る。

### 3-3. アイデアと仕様設計

- AI APIの原価があるため、**完全無料のビジネスモデルは成立しにくい**。
- 狙うのは次の両方を満たす領域。
  - 既存のAI単体では「絶妙に不便」
  - ユーザーがすでに外注費や時間削減のためにお金を払っている（例: リサーチャー、秘書、パーソナルトレーニング）
- コンセプトが固まったら、古典的なUXフレームワーク「**ギャレットのUX5レイヤー**」で仕様を固める。順に、戦略・要件・構造・骨格・表層。AIの学習データに深く定着しているため、人間が仕様書をゼロから書く必要はない。
- 進め方: 「UX5レイヤーの戦略レイヤーの仕様書を作って」と依頼し、構想を音声で話す。矛盾の少ない要件定義書が生成される。以降のレイヤーも同様に進める。

### 3-4. プロトタイプから本番実装へ

- スマホアプリが最終形でも、**プロトタイプは必ずWebで先行**する。端末へのビルドとインストールは検証サイクルを遅くする。Webで動作とUIを検証してから、AIにネイティブアプリへ移植してもらえば一瞬で済む。
- **本番へ進む判断基準**: ベータユーザーに「このサービスがなくなったらどれくらい困るか」を聞き、**過半数が「非常に困る」と答えたら**本番実装へ進む。
- **AIの分業**: アイデア力とデザイン性に強い Claude Code に実装を任せ、厳密なコード生成とバグ検出に強い Codex にテストとコードレビューを任せる。
- **根深い不具合の対応**: AIに場当たり的な修正をすぐさせない。「根本原因を分析して選択肢を示して。まだ実装はしないで」と指示し、**方針は人間が決める**。これがコードの破綻を防ぐ。

### 3-5. デザイン品質とセキュリティ

- **安っぽいAIデザインの回避**: 参考画像を集めた**ムードボード**を渡す。
- 個別の画面を描かせる前に、配色や共通パーツのルールを定めた**デザインシステム**を先に作らせ、全体の一貫性を担保する。
- UIや文言で迷ったときは、判断専用の**使い捨てHTML**を作らせ、ブラウザ上で見比べて選ぶ。意思決定の速度が大きく上がる。
- **セキュリティ**: 非エンジニアが最も不安に感じる領域だが、推論能力の高いAIに「攻撃者の視点でペネトレーションテストを実行して」と指示すれば対応できる。脆弱性をあえて突かせ、突破された穴を一つずつ塞がせる。
- 紹介動画の生成フレームワークや、行動分析ツールの埋め込みも、AIに任せられる。

### 3-6. 作り手の役割

- 実装や周辺作業はAIに任せ、経営者は「何を創るか」「妥協しない価値は何か」の意思決定にのみ集中する。

## 4. VINYL ARCHIVE への当てはめ

現状を踏まえた、ブラッシュアップ時の指針。新しい機能や改修を始める前に、ここを確認する。

| 前提概念 | このプロジェクトでの扱い |
|---|---|
| 狙う領域 | レコード収集家は、すでに盤や相場情報にお金を払っている。「ジャケット撮影だけで曲目・相場まで揃う」手間削減を核の価値とする |
| 原価の前提 | AI解析（Gemini + Google Search Grounding）には従量コストがある。無料提供を前提にせず、利用量・費用の上限管理と課金モデルを検討する |
| Web先行 | 現状のPWA（GitHub Pages + Supabase）を維持して検証する。ネイティブ化はベータ検証後 |
| 本番判断 | ベータユーザーへの「なくなったら困るか」調査を、ローンチ判断の基準にする |
| 仕様設計 | 機能追加の前に、UX 5レイヤーで戦略（誰の何を解決するか）から整理する |
| デザイン | ムードボードとデザインシステムを先に定義してから画面を直す（`styles.css` のトークン化を含む） |
| レビュー | 実装とレビューは別のAI（Codex等）で分担できると望ましい |
| セキュリティ | RLS・Storageのアクセス制御・Edge Functionの認証を対象に、攻撃者視点のテストを実施する |
| 不具合対応 | 原因分析と選択肢提示を先に行い、承認後に実装する |
| 発信 | 制作過程の公開を、ローンチ前の集客として計画に含める |

## 5. AIエージェントへの作業ルール

- 不具合の修正依頼では、まず根本原因と選択肢を提示する。ユーザーの承認なしに大きな修正を実装しない。
- 画面やUI文言で迷うときは、比較用の使い捨てHTMLを作ってユーザーに選んでもらう。
- 新しい画面を作る前に、デザインシステム（色・余白・共通パーツ）を確認し、それに沿う。
- 機能追加の提案は、「ユーザーがすでにお金や時間を使っている課題か」を基準に評価する。
- シークレット（Service Role Key、Gemini APIキーなど）はコードに置かない。
