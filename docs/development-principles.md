# 制作の前提概念と実践手順

VINYL ARCHIVE の改良を、課題の理解から利用後の改善までつなげるための作業指針。AIは調査・提案・実装・検証を担い、作り手は提供価値、価格、重要な仕様の分岐を判断する。

着想元は [PIVOT「非エンジニア経営者のための『実践AI開発術』：完成までの11ステップ」](https://pivotmedia.co.jp/movie/15167)。本編の工程名・確認方法・タイムコードは[出典確認メモ](references/pivot-15167.md)にまとめた。**以下の成果物、完了条件、テスト、指標は、このアプリへの適用案であり、動画の引用や実施済みの報告ではない。**

## 1. このアプリで守る価値

現時点の価値仮説は「レコードの撮影から曲目・市場価格の調査、保存、再発見までの手間を減らす」。収集家が盤を買うことと、管理・調査サービスに支払うことは別なので、支払意思は利用者への確認事項とする。

- 課題の解像度を上げる。誰が、いつ、何枚を、今どの方法で管理・調査しているかを具体的な行動から確認する。
- 写真を保存できること、AIの候補が得られること、候補の正しさを確認できることを、それぞれ検証する。写真だけで同一盤を確定できるとは約束しない。
- 調査できない情報を推測で埋めない。同一盤の根拠、調査出典、未確認の状態をユーザーが判断できることを重視する。
- 既存のPWAで小さく試して改善する。ネイティブ化、課金、新たな分析サービスの導入は、必要性と費用を確かめてから判断する。
- 作れる機能の数より、利用者が一連の作業を完了できるかで優先度を決める。

## 2. 11工程をこのアプリで回す

番号は本編の全11工程に対応する。既存アプリの改修では変更に関係する工程を取り出して使い、毎回ゼロから全資料を作り直す必要はない。完了条件の充足は証拠で判断し、この表の存在だけで完了扱いにしない。

| 工程 | このアプリで行うこと・残すもの | 次へ進むための確認 |
|---|---|---|
| 01 コンセプト設計 | 対象者、困る場面、現在の代替手段、改善したい作業、今回扱わない範囲を短い企画メモにする | 誰のどの負担を減らすか説明できる |
| 02 仕様設計 | 戦略・要件・構造を順に整理。必要な情報、優先度、画面間の流れと失敗時の戻り先を定義する | 要件が価値仮説に結びつき、正常時と失敗時の期待動作がある |
| 03 画面設計 | 撮影・一括追加、一覧、詳細、同期のうち対象画面のワイヤーフレームを作る。判断が割れる主要画面は複数案で比較する | 次にする操作、解析状況、未確認情報が分かる |
| 04 プロトタイプ実装 | PWA上で対象の流れを一通り試せる最小実装を作る。仮データ・模擬処理は明示する | 実機ブラウザで主要操作がつながり、模擬動作と実連携を区別できる |
| 05 価値検証 | 実際の盤で試してもらい、作業時間、再利用、離脱理由、なくなった場合の困り度を記録する | 利用の事実と不満があり、継続・修正・見送りの判断理由を残せる |
| 06 本番実装 | 実装とシナリオ検証を行い、実装時とは別の観点で差分をレビューする | 再現条件・期待値・実測結果があり、重要な未解決事項が明確 |
| 07 価格設計 | 解析・検索・保存・転送等の原価を実測し、利用量別の費用と利用上限・プラン案を比較する | 多量利用時の費用が分かり、支払意思と照合できる |
| 08 デザイン精緻化 | 複数の参考をムードボードにし、既存の色・文字・余白・共通部品を整理してから画面へ適用する | 一覧・詳細・ダイアログ・エラー表示が同じルールで読める |
| 09 セキュリティチェック | 認証、利用者間のデータ分離、写真、解析呼び出しを検証用データで確認する | 想定外の読み書きが拒否され、指摘の修正後に再検証できている |
| 10 マーケティング素材準備 | 実際の操作を示す紹介文・画像・短いデモを作り、届ける相手と経路を決める | 実装・検証できた機能だけを約束し、試す入口が分かる |
| 11 計測設計 | 登録から再利用までのイベント、集計単位、見る頻度を決め、検証環境で発火と集計を確認する | どこで困っているか判断でき、次の改善仮説につながる |

## 3. 仕様はUXの5層を下から積む

動画では仕様設計に最初の3層、画面設計に骨格、デザイン精緻化に表層を対応させている。見た目と機能と利用目的を一度に決めようとせず、下位層の判断を前提として上位層を作る。

| 層 | VINYL ARCHIVEで言語化する内容 |
|---|---|
| 戦略 | 誰のどんな調査・管理負担を減らすか。成功を何で確かめるか |
| 要件 | 今回必要な機能と情報、対象外、優先度、受入条件 |
| 構造 | 撮影→保存→解析→確認・修正→一覧／詳細で再利用する流れと、失敗時の回復 |
| 骨格 | 各画面の情報の順序、主操作、状態表示、戻り先 |
| 表層 | 色、書体、余白、共通部品、写真の扱い、状態の視認性 |

AIへの依頼例（本プロジェクト用）:

> 今回の対象者と困る場面をもとに、まず戦略層の案を整理してください。確認できた事実と仮説を分け、未決定事項は残してください。次に、その戦略に沿った要件・優先度・受入条件と、正常時／失敗時の利用の流れを提案してください。

## 4. 価値・価格・継続利用を検証する

### 価値検証

本編29:26–30:14では、日常的な利用と、5段階の困り度調査を挙げている。過半数が最も強い困り度を選ぶことは話者の判断目安であり、本アプリの達成済み目標や一般的な成功保証ではない。

本アプリでは、レコードを追加・調査する機会が毎日あるとは限らない。利用機会ごとに再び選ばれるかを確かめる。協力者数、対象者、利用期間、回答数と分母を残し、少数の好意的回答だけでローンチ可否を決めない。

- 手作業で調べた場合と比べた、1枚の登録・確認にかかる時間
- 曲目・相場候補を確認し、必要な修正をして保存まで完了できたか
- 次の収集・整理の機会に再利用したか、使わなくなった理由は何か
- サービスが使えなくなった場合の困り度（5段階）、その理由、戻る代替手段

### 価格設計

本編34:16–35:40の利用量分布2:6:2は試算の出発点として紹介されたもの。実際の利用分布、価格、利益率は未決定とする。無料枠を含む提供方法は、費用を負担できる根拠とともに比較する。

試算ではライト・ミドル・ヘビーごとに月間登録枚数、再調査率、成功／失敗／再試行回数、1回あたりの解析・検索費、保存容量・転送量、決済費用を入力する。APIの無料枠や単価には確認日と公式出典を付ける。

```text
月間処理費 = Σ（利用区分の人数 × 1人あたりの月間処理回数 × 1回あたりの実測費用）
月間費用 = 月間処理費 + 保存・転送等の費用 + 決済費用 + その他の運用費
月間売上 = Σ（各プランの人数 × 月額単価）
試算上の利益率 = （月間売上 − 月間費用）÷ 月間売上
```

処理費には失敗や再試行も含め、課金単位に合わせて検索等を内訳化する。売上ゼロのケースは利益率を算出せず、必要な負担額を示す。固定費と変動費を区別し、平均値に加えて多量利用・連続再試行時の費用を確認する。利用上限、警告、停止条件は設計案として比較し、未実装の制御を有効だと説明しない。

価格案は利用者に提示して確かめる。本編の4つの価格質問を使う調査への言及と、実測原価、提供価値を合わせて判断し、AIの計算だけで価格を確定しない。

### 計測設計

次は導入前のイベント案。分析ツールの採用・タグ設置・収集開始を意味しない。各イベントに発火条件、重複の扱い、集計期間と分母を定める。

| イベント案 | 発火条件 | 分かること |
|---|---|---|
| `record_saved` | ローカルの保存処理が成功 | 登録件数と初回登録への到達 |
| `cloud_sync_completed` | 対象のクラウド保存・取得が完了 | ローカル保存から同期までの到達率 |
| `analysis_finished` | 解析が成功・要確認・情報なし・エラーのいずれかで終了 | 結果別の件数、所要時間、再試行率 |
| `record_corrected` | 利用者がAI候補を修正して保存 | 修正の必要性。正解率は別途、盤を照合して評価 |
| `collection_revisited` | 初回とは別の利用機会に一覧／詳細を開く | 継続利用。初回登録者を分母として期間を揃える |

レコードID・解析試行ID等で二重計上を防ぐ方法を検討する。画像、曲名・自由記述、メール、認証情報、署名付きURLは分析イベントへ送らず、結果区分や件数等で集計できる設計を優先する。計測を追加する際は収集目的・保存期間・説明方法も決める。週次など決めた周期で離脱箇所と費用を見て、次の改善を1つ選ぶ。

## 5. 実装・レビュー・品質確認

実装とレビューは役割を分ける。動画のツール比較は話者の利用経験であり、特定の製品・モデルに役割を固定しない。利用可能な別のAIや人によるレビューを活用し、同じ担当で確認した場合は独立レビュー済みと呼ばない。並列作業では対象ファイルと依存関係を分け、統合後の動作を確認する。

根深い不具合、仕様変更、データ構造・費用・権限に影響する修正は、再現条件と原因を調べ、選択肢・影響・推奨案を示してから方針を決める。既に承認された範囲の実装や、局所的で可逆な修正で毎回承認を取り直さない。

AIへの依頼例（本プロジェクト用）:

> 再現条件と関連する状態・データの流れから根本原因を調べてください。応急処置と根本対応を分け、選択肢ごとの影響と検証方法を説明してください。設計変更が必要な場合は、方針を決めるまで実装を保留してください。

### シナリオを先に作る

本編33:32–34:11を踏まえ、AIの候補が揺れる処理は正常系だけで確認しない。以下は今後の検証案で、結果はまだ記録されていない。変更に関係するシナリオを選び、環境・入力・手順・期待結果・実測・残課題を残す。

| シナリオ | 期待結果として確認すること |
|---|---|
| 読めるジャケットを1枚保存 | 写真保存後に解析が始まり、候補と出典を確認できる |
| 型番が読めない／同名の別盤がある | 盤を断定せず、要確認として扱える |
| B面が照合できない／相場の根拠不足 | 推測で曲名や価格を補わず、未確認・未調査と分かる |
| 有用な解析結果が全くない | 「情報なし」と処理エラーを区別できる |
| 通信断・APIエラー・途中でアプリを閉じる | 保存データを失わず、状態が分かり、復帰後に再試行できる |
| 連続撮影・複数選択・再調査の繰り返し | 写真と盤情報が対応し、重複・費用・処理中状態を確認できる |
| 同一アカウントを別端末で開く | 情報・写真・修正が意図した状態で同期される |
| 未ログイン・期限切れ・別利用者のデータ指定 | 許可されないデータを読み書きできず、解析も実行できない |
| iPhoneとPC、旧キャッシュからの更新 | 主要操作、カメラの代替手段、更新後の表示が使える |

### セキュリティと公開の確認

本編はAIによる攻撃者視点の検証に加え、専門家のレビューにも言及している。AIへの依頼だけで安全と判定しない。本アプリでは `supabase/schema.sql`、`cloud-sync.js`、`supabase/functions/analyze-record/index.ts` を起点に、検証環境で利用者A・Bと未認証のアクセスを比較する。別人のレコード・写真の取得／更新／削除、所有者の付け替え、他人のIDによる解析呼び出しが拒否されることを確かめる。

テスト対象とデータを明示し、許可された範囲で実行する。Service Role KeyやAI APIキーをブラウザ・リポジトリ・ログへ出さない。写真の署名付きURLも公開資料に載せない。

ローカル確認、コミット、PR、デプロイ、公開環境の実機確認は別の状態として報告する。検証に使った環境・差分・結果を残し、未検証の同期や解析を完了扱いにしない。公開時は対象コミット、キャッシュ更新、認証、写真保存、解析、端末間同期を確認する。

## 6. デザインと届け方

`styles.css` には既に `--ink`、`--paper`、`--orange` 等の色変数がある。新設を前提にせず、関連CSSと共通部品を調べて、一貫した色・文字・余白・状態表示へ整理する。複数の参考のどの要素を採るか言語化し、特定の画面を丸写ししない。抽象的な「かっこよさ」だけでなく、写真・文字の読みやすさ、操作の優先順位、スマートフォンでの使いやすさを基準にする。

判断が割れる画面や文言は、違いが分かる少数案を使い捨てHTMLで並べる。比較用ファイルは一時領域へ置き、採用案と理由を本体に反映する。実装済み・未実装・解析失敗などの状態も含めて見た目を確認する。

紹介素材は「誰のどんな手間が、実際の操作でどう減るか」を示す。AI生成素材はたたき台として使い、特に品質が必要な箇所は人による制作・確認を組み合わせる。発信で利用者を集める方法と、検証参加者に限定して育てる方法は選択肢として比較し、SNS公開を自動的な必須条件にしない。
