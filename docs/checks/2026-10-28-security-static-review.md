## 修正した指摘

### 1. URLのジャンル指定からのXSS（重大）

- 再現条件：`#/?genre=` に HTML を入れたリンクを開く。例：`#/?genre="><img src=x onerror=...>`
- 原因：URLから読んだ `filter` を、ジャンル選択ボタンの `innerHTML` にエスケープせず埋め込んでいた。ジャンルは自由入力になったため、カード・一覧・詳細の `genre` 表示も同じ問題があった。
- 影響：ログイン中の利用者がリンクを開くと任意のスクリプトが実行され、ブラウザに保存されたSupabaseセッションで、その利用者のレコード・写真を読み書きされうる。
- 対応：`app.js` でジャンルと発売年の表示を `esc()` 経由に変更した。旧キャッシュに古い `app.js` が残らないよう、Service Workerのキャッシュ版を `v38` に上げた。

| 項目 | 内容 |
|---|---|
| 環境 | ローカル（`python3 -m http.server`）、ヘッドレスChrome、未ログイン、データなし |
| 入力 | `http://127.0.0.1:8765/#/?genre="><img src=x onerror=document.title='PWNED'>` |
| 期待結果 | スクリプトは実行されず、文字列としてボタンに表示される |
| 修正前の実測 | ページタイトルが `PWNED` に変わり、スクリプトが実行された |
| 修正後の実測 | タイトルは変わらず、ボタンにエスケープされた文字列が表示された |

### 2. 他人の写真を解析させられる（中）

- 再現条件：利用者Aが自分のレコードの `cover_path` を `<利用者BのID>/<ファイル名>` に更新し、再調査を実行する。
- 原因：RLSは `cover_path` の値を制限しない。`analyze-record` はService Roleで写真を取得するため、Storageの所有者ポリシーが効かない。
- 影響：Bの写真がGeminiに送られ、読み取った作品情報がAのレコードに書き込まれる。写真そのものの署名付きURLは、アプリ側ではAの権限で発行するため取得できない。
- 対応：`analyze-record` で、`cover_path` が `<レコードのuser_id>/<ファイル名>`（アプリが作る形式）の場合だけ写真を取得するようにした。それ以外は `error` として終了する。
- 確認：判定式を、正規のパス、他人のフォルダ、`../` を含むパス、階層の深いパス、`null` の7パターンで単体確認し、すべて期待どおりだった。Edge Functionは構文確認のみで、**デプロイおよびデプロイ後の動作確認は未実施**。
